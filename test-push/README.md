# 1.3.2 재방문 푸시 테스트

위에서부터 순서대로 진행한다. 계정 삭제는 하지 않는다. 앞 단계에서 만든 상태(권한, 동의, 실행 횟수)를 다음 단계가 이어서 쓴다.

## 0. 준비 (한 번만)

- Xcode를 껐다 켠 뒤 빌드하고, 단위 테스트를 돌린다.
- 시뮬레이터에 푸시 보내기: 이 폴더의 `.apns` 파일을 시뮬레이터 창에 끌어다 놓거나, 레포 루트에서 아래를 실행한다.
  `xcrun simctl push booted parkjju.dignify test-push/new_release.apns`
  시스템 알림 권한이 **허용**이어야 배너가 뜬다.

| 파일 | 내용 |
|---|---|
| `new_release.apns` | 신곡 3곡(1·2·3, Leo Kottke) |
| `new_release_single.apns` | 신곡 1곡(11) |
| `new_release_missing.apns` | 없는 곡만(999999999) |
| `weekly_pick.apns` | 주간 추천 5곡(6~10) |
| `curation.apns` | 큐레이션(곡 목록 없음) |

- 확인할 곳: 어드민의 유저 상세(광고성 동의 값), PostHog 실시간 이벤트.

## 상태 만드는 법

계정은 지우지 않는다. 기존 계정 하나로 전부 본다.

| 이름 | 방법 | 결과 |
|---|---|---|
| **새로 설치** | 앱 삭제 → Xcode로 실행 → 기존 계정으로 로그인 | 기기 기록이 비고, 권한 「설정 전」 |
| **신규 유저** | 마이 › 「신규 유저 상태로 초기화 (DEBUG)」 → 앱 완전 종료 → 실행 | 막 가입한 유저로 본다. 권한은 **그대로** |
| **업데이트 유저** | 마이 › 「업데이트 유저 상태로 초기화 (DEBUG)」 → 앱 완전 종료 → 실행 | 1.3.1에서 막 올라온 기존 유저로 본다. 권한은 **그대로** |

- 두 초기화 행은 서버 광고성 동의도 거부로 돌린다.
- 시스템 알림 권한은 앱을 지워야만 「설정 전」으로 돌아간다. 그래서 권한을 건드리지 않는 단계(동의 팝업에서 「나중에」)를 앞에 둔다.
- 온보딩 곡 고르기 화면은 마이 › 「신규 온보딩 열기 (DEBUG)」로 따로 본다. 여기서 고른 곡은 **실제로 좋아요된다**.

## 7. 실기기 — 실제 발송 (운영 서버)

로컬 서버는 APNs 키가 없어서(`.env`에 `APNS_*` 없음) 푸시를 못 보낸다. 그래서 운영 서버의 플래그를 잠깐 켠다.
지금은 운영에서 켜도 받는 사람이 테스트 계정뿐이다. 광고성 동의는 1.3.2에서만 할 수 있는데 1.3.2는 아직 출시 전이고, 최소 빌드 29도 이 빌드만 통과한다.

### 가. 준비

1. 실기기에 Xcode로 디버그 빌드를 설치한다. baseURL은 지금처럼 운영을 본다. 디버그 빌드는 기기 토큰을 sandbox로 등록하는데, 운영 서버에 sandbox용 APNs 클라이언트도 같이 있다.
2. 로그인 → 동의 팝업 「알림 받기」 → 시스템 팝업 **허용**. 이미 지나갔으면 마이 › 「업데이트 유저 상태로 초기화」 → 재실행.
3. 이 계정이 좋아요한 곡이 **4곡 이상**인지 확인한다. 주간 추천을 받을 조건이다.
4. 어드민에서 두 가지를 본다. 광고성 동의 true인 유저가 **테스트 계정뿐인지**, 이 계정의 `user_id`가 짝수인지 홀수인지.
5. **기기 시각이 08~21시 사이**인지 본다. 크론 발송은 기기 시간대 기준 21시 이후엔 안 나간다.

### 나. 운영 플래그 켜기

```
gcloud run services update dignify-backend --region us-central1 \
  --update-env-vars PUSH_AD_ENABLED=true,PUSH_AD_MIN_BUILD_IOS=29
```
새 리비전이 뜰 때까지 1분쯤 걸린다. 배포 워크플로는 환경 변수를 건드리지 않아서, 그 사이에 main에 푸시해도 값이 그대로다.

### 다. 주간 추천 받기 → 탭

```
curl -X POST -H "X-Cron-Secret: <CRON_SECRET>" \
  "https://dignify-backend-460750160818.us-central1.run.app/internal/cron/weekly-picks?slot=<am|pm>"
```
`user_id`가 **홀수면 `am`, 짝수면 `pm`**이다. 응답의 `sent`가 1 이상이어야 한다. 0이면 준비 단계 중 하나가 빠진 것이다. 결과는 디스코드에도 온다.
주간 추천은 **유저당 한 주에 한 번**만 나간다. 다시 받으려면 `weekly_picks`에서 이번 주 행을 지워야 한다.

| # | 할 일 | 기대 결과 |
|---|---|---|
| 7-1 | 잠금 화면 알림 보기 | 제목이 `(광고)`로 시작한다 |
| 7-2 | 알림을 길게 누르기 | 「수신거부」 버튼이 있다. 누르지는 않는다 |
| 7-3 | 알림 탭 | 5곡이 앞에 오고 배지는 「이번 주 추천 1/5」. 다 넘기면 평소 피드 |
| 7-4 | PostHog | `app_opened_push{type: weekly_pick}`, `push_id`가 실제 값 |

### 라. 수신거부

알림이 한 번 더 필요하다. 어드민 푸시 발송 화면에서 **type `curation`, 대상 user id = 내 계정**으로 보낸다. 큐레이션도 광고성이라 `(광고)` 제목과 「수신거부」 버튼이 붙는다.

| # | 할 일 | 기대 결과 |
|---|---|---|
| 7-5 | 알림을 길게 눌러 「수신거부」 | 앱이 안 열리고, 「…수신거부가 …에 처리되었습니다」 알림이 뜬다 |
| 7-6 | 어드민 | 이 유저 광고성 동의 false |
| 7-7 | 앱 › 마이 › 알림 | 토글이 꺼져 있다 |
| 7-8 | 같은 방법으로 한 번 더 보내기 | 안 온다(동의 false) |

### 마. 끝나면 되돌리기

```
gcloud run services update dignify-backend --region us-central1 \
  --update-env-vars PUSH_AD_ENABLED=false
```
`PUSH_AD_MIN_BUILD_IOS=29`는 그대로 둬도 된다. 출시 때 쓸 값이다.
